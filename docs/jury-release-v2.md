# Сценарий жюри v2

Профиль: `configs/acceptance/lidar2sim-rules-v2.yaml`. Правила зачёта и ранжирования — `docs/rules.md`. B и скрытая C остаются в каталоге оператора с правами 700. Полные отчёты C и её рецепт нельзя публиковать в репозитории, публичном архиве или демонстрационных логах.

## Подготовка

1. Принять исходники/образ и конфигурацию команды, записать commit и SHA256. Проверить сборку до отключения сети. Образ не должен содержать B/GT, скрытые данные или подготовленные ответы. Не запускать непроверенный образ с Docker-сокетом, GPU или домашним каталогом оператора.
2. Проверить `SHA256SUMS` публичного и частного пакета. Зафиксировать хеш образа через `docker image inspect --format '{{.Id}}' IMAGE`. Сохранить версии, команды и ограничения ресурсов.
3. На Spark использовать существующий слот Isaac. Guard приостанавливает только заранее разрешённые `isaac-stream`/`isaac-flight` и восстанавливает их после завершения или ошибки. Чужая сессия блокирует запуск; её нельзя автоматически останавливать. Foxglove не останавливается.

## Эталонный сценарий baseline/final

Команды выполняются на Linux-хосте с Docker, из checkout проекта. Переменные ниже задаёт оператор; `$JURY` содержит распакованный частный пакет. Для реконструкции используется CPU-образ из `deployment/Dockerfile.cpu`; закрытые данные не входят в его build context. Для offline-сборки есть отдельный Dockerfile с проверенным wheelhouse и SHA256SUMS.

```sh
python3 tools/calibrate_release.py --jury "$JURY" --out "$RUNS" --image "$IMAGE_ID" --repeats 5
python3 tools/jury_performance.py --data "$DENSE" --out "$PERFORMANCE" --image "$IMAGE_ID"
python3 tools/jury_protocol.py --jury "$JURY" --batch "$RUNS" --performance "$PERFORMANCE" --out "$PROTOCOL" --repeats 5
python3 tools/jury_compare.py "$PROTOCOL/manifest.json" --out "$PROTOCOL/table"
```

Для экспериментального финального конфига передавайте один и тот же файл
через `--final-config PATH` **обоим** скриптам: `calibrate_release.py` и
`jury_performance.py`. Без этого флага каждый использует
`configs/poc-high-detail.yaml`. Например, для кандидата с поддержкой границы пола:

```sh
FINAL_CONFIG=configs/poc-planar-floor-support.yaml
python3 tools/calibrate_release.py --jury "$JURY" --out "$RUNS" --image "$IMAGE_ID" --final-config "$FINAL_CONFIG" --repeats 5
python3 tools/jury_performance.py --data "$DENSE" --out "$PERFORMANCE" --image "$IMAGE_ID" --final-config "$FINAL_CONFIG"
python3 tools/jury_protocol.py --jury "$JURY" --batch "$RUNS" --performance "$PERFORMANCE" --out "$PROTOCOL" --repeats 5
python3 tools/jury_compare.py "$PROTOCOL/manifest.json" --out "$PROTOCOL/table"
```

Калибровка сохраняет путь и SHA256 выбранного конфига в `configuration.json`;
`environment.json` содержит только образ и ограничения исполнения.
Протокол берёт хеш из метаданных партии и сверяет его с отчётами и 10M-замером.
Можно разбить серию на
завершённые партии: `--start-repeat 2 --repeats 4` продолжает нумерацию после
первого повтора. Передать каждый каталог отдельным `--batch` в
`jury_protocol.py`. Дубликат повтора, недостающий JSON, изменённые артефакты и
разные окружения не дают полного зачёта. Не копировать физический отчёт
первого запуска на остальные повторы.

Завершение процесса и наличие `baseline_report.json` сами по себе не означают
зачёт: в `groups` финальный вариант должен иметь `complete_repetitions=true`,
`performance_passed=true` и `eligible=true`, а все его строки — `valid=true` и
`scene_passed=true`. Baseline может не пройти критерии качества: это измеряемый
результат сравнения, а не ошибка выполнения. После обрыва SSH сначала проверьте
состояние партии (`complete.json`, `failure.json`, `.abort`,
`physics-progress.json`) и работающие процессы на сервере. Не запускайте вторую
копию поверх активной серии и не перезаписывайте существующий каталог результатов.

Сценарий запускает 20 отдельных реконструкций и 20 свежих процессов Isaac для матрицы baseline/final × A/C × 5. Реконструктор получает только A, минимальный manifest, траекторию и конфигурацию: сеть отключена, UID 65534, корневая FS read-only, capabilities удалены, 4 CPU, 16 GiB, 1800 с. На текущем Docker Snap флаг `no-new-privileges` приводит к отказу запуска даже `/bin/sh`, поэтому этот дополнительный флаг не используется. Это ограничение записано явно; данный стенд не заявлен как песочница для произвольного враждебного кода.

Затем отдельный доверенный оценщик подключает B/GT только для метрик. Isaac открывает именно полученный USD, повторяет 10 проверок пола, 10 препятствий и 5 маршрутов. После физики отчёт объединяется с профилем v2. `baseline_report.json`, `comparison.json` и Markdown-таблица создаются из JSON, а не вручную. Неуспешное качество — результат измерения, а не повод удалять строку или смягчать порог.

Для других команд применяется `jury_reconstruct.py` с их закреплённым образом и конфигурацией, затем те же оценщик и физический runner. CLI образа должен принимать аргументы `-m lidar2sim --input … --out …`; иной интерфейс адаптируется и фиксируется до зачётного запуска. В private manifest сравнения указываются их реальные идентификаторы, конфигурации, данные, отчёты и отдельный замер 10M. Скрипт калибровки сам по себе сравнивает baseline с выбранной финальной конфигурацией; другие команды оцениваются отдельно.

## Открытие USD и защита

- Проверить хеш USD относительно объединённого отчёта; открыть этот же файл в Isaac. Показать visual и collision отдельно, единицы m/Z и статический collider.
- Показать повтор коллизий и JSON физики. Сохранить все четыре выходных файла, конфигурацию, stdout/stderr, geometry/physics JSON, SHA256, версии и измерения времени/RSS.
- Записать видео публичной A с исходным облаком, сетками, сценой и проверкой движения. Видео должно ссылаться на тот же USD и профиль. Видео прошлой версии не подтверждает новую.
- Для C показывать только разрешённые агрегаты. Полные материалы сохраняются в частном архиве жюри.
- Отсутствующие данные, падение процесса, тайм-аут и нарушение контракта сохраняются как error/failed. Участник получает причину; повтор допускается только по объявленному организационному правилу, с сохранением предыдущего результата.
- Перед началом соревнования оператор должен объявить канал приёма, расписание Isaac и правила повторной сдачи. Этот технический сценарий не выдаёт отсутствующий регламент за согласованный.

Финальная H30 дополнительно требует отдельного аккаунта участника и прохождения без помощи автора. Автоматическая распаковка/проверка в свежем окружении — необходимая техническая проверка, но не замена этой репетиции.
